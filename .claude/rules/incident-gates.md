# 每个事故都要有自动门槛

每个事故都必须以一项自动检查结束；同一个错误出现三次，必须用硬门槛挡住。

## 什么算数

- 下面这些都算事故：
  1. 说过“测完了”才交给 Andy 的构建（例如 TestFlight），被他发现了 bug。
  2. 修过的问题在后面的构建里又出现。次数要累计。
  3. 发版失败或半路被拦下，例如上传 App Store Connect 失败，或者 CI 没跑完整就发了版。
  4. CI 是绿的，功能其实是坏的，说明测试没测到点上。
  5. Andy 发现的资料错误，例如例句识别不出来、翻译残留中文、注音错误。
- 不算事故：还没交给 Andy 时开发中的失败，以及 Andy 提的新需求或界面意见。
- 门槛是指自己会运行、失败时会拦下的检查，例如单元测试、端到端测试、`tools/` 下的校验脚本、CI 或发版工作流里的一步。文档、交接说明、记忆或提醒都不算门槛。
- 一个事故只有在门槛已经存在、并证明它在复现上会失败、修好后会通过时，才算关闭。把证据写进提交或 PR 说明。
- 同一个错误第三次出现时，先加硬门槛，再继续处理。只有 Andy 能做的改动，准备好具体方案问他一次。

## 交付报告

写明处理了哪些事故、加了什么门槛（文件或命令），或者为什么不需要。
