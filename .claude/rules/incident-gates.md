# 每个事故都要有自动门槛

每个事故都必须以一项自动检查结束，同一个错误出现三次就必须用硬门槛（会自动拦下的测试或可执行逻辑）挡住。本规则来自 `sixianli/himawari-agent`，云端线程和 Mac 上的会话都会通过这里知道它。

## 什么算数

- 事故是指：线上版本或 TestFlight 构建里的故障、失败或被撤回的发版、直到发版流程后期才被拦下的问题，或者用户发现的、本可以由检查发现的缺陷。
- 门槛是指自己会运行、失败时会拦下的检查。在本项目里例如：单元测试（`JapaneseGrammarScannerTests/`）、端到端测试（`JapaneseGrammarScannerUITests/`）、`tools/` 下的校验脚本（`validate_grammar.py` 等）、CI（`.github/workflows/ios.yml`）里的一步，或发版工作流里的检查。文档、交接说明、记忆笔记或提醒都不是门槛。
- 一个事故只有在它的门槛已经存在、并且已证明它在事故的复现上会失败、在原因去除后会通过时，才算关闭。把这份证据写进提交说明或 PR 说明。
- 同一个错误第三次出现时，无论是事故还是代理自己的失误，在继续处理这个错误的工作之前都需要一道硬门槛。当只有用户能做这项改动时，把它准备好，带着具体方案问一次。

## 交付报告

写明线程处理的每个事故、加上的门槛（文件或命令）或为什么不需要门槛。
