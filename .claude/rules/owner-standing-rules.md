# Andy 定的长期规则

这些是 Andy 在 `sixianli/himawari-agent` 项目里定下、适用于每个项目的长期规则，这里只保留和具体项目无关的部分，并按本项目（离线 iOS App，不调用任何大模型）改写了例子。只有 claude.ai 项目里新开的线程能读到项目指令，Andy 在 Mac 终端直接开的 Claude Code 会话读不到，所以写进仓库。它们约束所有代理；和仓库根目录 `CLAUDE.md` 冲突时，以 `CLAUDE.md` 为准。

<a id="money"></a>
## 花钱先问

- 任何评测、测试、实验、批量模型调用或付费服务，预计要花 Andy 的钱超过 0.5 美元时，先在项目聊天报出预计费用和用途，等 Andy 明确同意再开跑；费用说不准时，按会超过处理。
- 评测和测试绝不和生产共用预算或密钥（API key）：曾有一次评测花光了账号预算，生产因此中断。
- 不得通过按 token 付费的渠道调用 Claude、OpenAI 或同价位的贵模型；确需按量付费时，只用低价模型或免费额度，并先按上一条问。Andy 已付费套餐里的额度不在禁用之列，而且要优先用。

<a id="fixing-bugs-and-new-features"></a>
## 修 bug 和做新功能

- 修 bug 先查根因，不许只修表面。修法要先上网查当前的做法（官方文档、成熟开源项目，附一手来源），已有成熟方案就采用，拿不准的拿出来和 Andy 讨论；不得凭记忆或过时的训练数据决定修法。PR 说明里写清“业界怎么做、我们为什么这样做、放弃了什么”。
- 大改动先出方案、讨论后再动工：
  - 什么算大改动：改动较大的模块或功能，或者动到项目的核心特性。在本项目里例如：语法识别规则（`GrammarMatcher`、`patterns`/`subsumes` 的写法）、OCR 和高亮定位、试用与买断（内购）、复习算法、本机数据存储结构、隐私和合规相关的代码、发版流程。新增 Andy 不熟悉的功能、改机制或规则也算。拿不准算不算的，按大改动处理，先问 Andy。修小 bug 不用走这条。
  - 写方案时，先上网搜最新资料，参考 Apple 官方文档和 GitHub 上成熟的开源实现，附一手来源；不从零写。
  - 方案先和 Andy 讨论，他同意之后才能改代码、改文件或开 PR。较大的界面改动按 `CLAUDE.md` 先出设计图。

<a id="numbers-and-acceptance-in-the-ui"></a>
## 界面上的数字和验收

- 界面上给用户看的每个数字和判断词（例如“识别到 5 个语法点”“已掌握”“今日待复习 N 个”）都要有可以验证的定义，没有就不显示。
- 说一个界面功能“做完了”时，要附上正向和反向两种验收结果。反向验收是给一个不该命中、不该触发的输入（例如一段不含该语法的日文），期望结果为空或不触发。没有反向验收的不算完成；能写成端到端测试的就写成测试。

<a id="authorization"></a>
## 授权

- Andy 尽量只和协调者沟通。所以他在项目聊天里对协调者说的话，由协调者附上他那条原话转给对应线程，就算他的授权，不要让他再去别的线程重说一遍。
- 唯一的例外是删除 Andy 的 Mac 上的文件：只认他在 Mac 线程（通过 Remote Control 在他 MacBook 上运行的那个线程）里亲手打的字。
- 会删东西或不可撤销的操作（例如发版、提交 App Store 审核），所有要 Andy 选的选项先选完，再执行。
- 合并 PR 和发版要等 Andy 说可以；等的时候先做不依赖这一步的其他工作。

<a id="independent-judgment"></a>
## 独立判断，不盲从

- 每个线程和协调者都要有自己的判断，不得盲从 Andy 的指示、决定，或他已经同意的方案。动手之前先核对它和现有功能、测试、已有规则有没有冲突。
- 判断 Andy 的决定不对，或者有更好的做法时，必须明确指出：哪里不对、会出什么问题、建议怎样做，然后等他定；不得默默照做。
- 例：一个改动会抢掉另一个已有功能的行为，实施前只要问一句“会不会影响 X”并跑一遍相关测试就能发现，却没有人问。
