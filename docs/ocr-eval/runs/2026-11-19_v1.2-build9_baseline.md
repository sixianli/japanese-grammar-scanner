# 基准评测：v1.2 build 9（当前上线版本）

- 日期：2026-11-19
- 代码版本：`ba5d42e`（识别逻辑与 TestFlight build 9 相同）
- 数据集：95 张用户实拍照片（`tests/ocr/samples/`），标准正文 `tests/ocr/groundtruth/`
- 原始识别结果：`2026-11-19_v1.2-build9_baseline.raw.zip`；完整指标：`2026-11-19_v1.2-build9_baseline.json`
- 运行环境：GitHub Actions，Xcode 27 / iOS 27.2 模拟器（Apple Vision 在模拟器与真机上的结果可能有差异，见「已知问题」）

## 1. 现状（被评测的方案）

| 环节 | 当前做法 |
|---|---|
| 图片预处理 | 只转正方向、长边限制 3000 像素；不裁切、不校正透视 |
| 文字识别 | Apple Vision `VNRecognizeTextRequest`，精确模式，语言 `ja-JP` + `en-US`，开启语言校正 |
| 拼接 | 按 Vision 返回的行顺序直接相连，上一行以句末标点结尾时换行 |
| 语法识别 | 每个语法点的正则规则逐条匹配；被包含的语法点（subsumes）去重 |
| 高亮框 | 直接采用 Vision 返回的逐字位置（`boundingBox(for:)`），拿不到时按字数比例估算 |

## 3. 发现

1. **多语言对照页是最大短板**（单词书召回 77.7%）：Vision 把同一行的日文和英文/中文/越南文释义读成一行，
   还会横跨左右两栏读取，导致日文句子被打断、语法匹配不上。
2. **注音不是以单独的行出现**：Vision 基本不单独输出注音行，而是让注音干扰正文识别
   （如「確か」→「雞か」、「一緒」→「一種」、「置いた」→「買いた」）。按行高过滤注音的方案几乎无效（假名插入率 5.8% → 5.2%）。
3. **误报主要来自邻页**：多张照片边缘入镜的另一页讲义（「〜とは限らない」「〜ほうがいい」「〜てもいい」）
   贡献了大部分误报；还有「〜目」（序数）在题号、页码上的误报。
4. **部分弯曲严重的页面整段漏读**（如 IMG_8918 只识别出 16 行）。
5. 离线试验：过滤非日文行 + 去掉行内非日文片段后，字精确 75.4% → 85.3%、噪声插入率 13.7% → 2.8%、
   语法精确率 95.6% → 96.1%，但语法召回率不变（90.5%）——说明噪声主要影响显示的文字，对语法漏识别帮助有限。
6. 书页透视校正在模拟器上 **0/95 张生效**（Vision 的书页检测没有返回可用结果），需要排查后再评估。

## 4. 已知问题

- **真机高亮框偏移**：用户在 build 9 真机上反馈示例页的框与文字错位，但同一页在模拟器上对齐正常。
  原因是真机 Vision 返回的逐字位置会偏移，而 App 直接采用。已在下一版改为「高度取整行、横向位置与等宽估算校验，
  偏差超过半个字就用估算」，评测中新增「弃用率」统计。
- 「精确定位率」只说明位置来自 Vision，不代表框对得准；框选正确率需要把框画到照片上抽样核对（下一轮补充）。
- 标准正文由人工逐字转写，各批转写在符号（Ⅰ/Ⅱ、★、□）上约定不一，评测前已统一去掉这些符号；
  多栏页面的阅读顺序也可能与 Vision 不同，所以同时给出与顺序无关的字召回/字精确。

## 5. 下一步（按预期收益排序）

1. 过滤非日文内容（行级 + 行内片段），并改进多栏页面的行拼接顺序
2. 书页检测与裁切：去掉邻页文字（减少误报），斜拍页透视校正
3. 分块识别：把页面切成有重叠的几块分别识别再合并，减少弯曲、小字页面的漏读
4. 语法规则：「〜目」等容易在题号、页码上误报的规则加上下文限制
5. 框选正确率：抽样画框核对，建立指标
